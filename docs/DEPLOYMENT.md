# Deploying OCRIS to Render

This guide puts OCRIS on the internet for the school: one Render web service in Singapore, with a persistent disk, and a MongoDB Atlas database in Singapore. It takes about an hour the first time. For a computer at the school instead, see section 10 of [INSTALLATION.md](INSTALLATION.md).

**Last updated:** October 18, 2026. The set-up has been checked on Windows in production mode (`DEBUG=False`, the built site served by Django, data on a separate folder), but the Docker image itself has not been built yet: Docker is not installed on the development computer. The first deploy on Render is its first real build.

## 1. What runs where

| Part | Where | Holds |
|---|---|---|
| Web service `ocris` (Docker, see `Dockerfile`) | Render, Singapore, instance `1c-2g` (1 CPU, 2 GB) | The site and the API on one address, Tesseract 5.5 |
| Persistent disk `ocris-data`, 10 GB, mounted at `/var/data` | Render, attached to the web service | Accounts and sign-ins (`db.sqlite3`), uploaded scans (encrypted), the audit file, the nightly backups |
| Database | MongoDB Atlas, AWS Singapore | Records, scan details, the audit log, sections |

Everything else in the container is replaced on every deploy; only `/var/data` is kept. Render also takes a snapshot of the disk every day and keeps it for at least seven days.

Things to know before you choose this set-up:

- **It costs money every month.** A disk needs a paid instance, and the 512 MB instance is too small (reading one form takes about 300 MB). Check the prices on Render's and Atlas's sites.
- **One copy of the server.** A service with a disk cannot be scaled to two instances, and every deploy stops the server for a minute or two.
- **The pupils' records are stored outside the Philippines** (Singapore). Get the school's written approval for this before real records go in (Data Privacy Act of 2012).

## 2. Before you start

- Access to the GitHub repository, with the commit that adds `Dockerfile` and `render.yaml` on the `main` branch.
- A Render account and a MongoDB Atlas account. Use an account the school can take over later, not a personal one that may disappear.
- Python with the `cryptography` package on your own computer (it is in `backend/requirements.txt`), to make the encryption key.

## 3. MongoDB Atlas

1. Create a project and a cluster: provider **AWS**, region **Singapore (ap-southeast-1)**. The free tier (M0) is big enough for a pilot, because the scans themselves are kept on the Render disk, not in MongoDB. It has no Atlas backups of its own; OCRIS's nightly backup includes the MongoDB data.
2. Add a **database user** for OCRIS, with a long password made of letters and digits only (other characters would have to be escaped in the connection string). Give it read and write access to the database `ocris_bcs` only, not to the whole cluster.
3. Add a **network access** entry. Render's addresses are only shown once the service exists, so for now allow `0.0.0.0/0` (anywhere); step 6.5 replaces it.
4. Copy the connection string (Connect → Drivers). It looks like `mongodb+srv://ocris:<password>@cluster0.abcde.mongodb.net/?retryWrites=true&w=majority`. Put the user's password in place of `<password>`. Keep this string secret: it opens the database.

## 4. The encryption key

Uploaded scans and backups are encrypted with `DATA_ENCRYPTION_KEY`. Make a new one for the cloud (do not reuse the key of a development computer):

```powershell
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

**Keep two copies away from Render**, for example in the school's password manager and on paper in the OIC's safe. Without this key, no scan and no backup can ever be read again, not even by Render.

## 5. Create the service on Render

1. In the Render Dashboard choose **New → Blueprint**, connect GitHub and pick the OCRIS repository. Render reads `render.yaml` and shows one web service, `ocris`, with the disk `ocris-data`.
2. Fill in the two values it asks for:
   - `MONGO_URI`: the connection string from step 3.4.
   - `DATA_ENCRYPTION_KEY`: the key from step 4.

   `SECRET_KEY` is generated by Render. The other settings come from `render.yaml` and the `Dockerfile`; see section 9.
3. Apply. The first build takes several minutes (it installs Tesseract and builds the site). In the service's **Logs** a good start ends with lines like:

   ```
   Daily upkeep at 02:00 (Manila); backups go to /var/data/backups
   Listening at: http://0.0.0.0:10000
   ```

   The site is then at the address shown at the top of the service page, `https://ocris-xxxx.onrender.com`.

If the deploy fails, see section 10.

## 6. First sign-in

1. **Create the first account.** Open the service's **Shell** tab and run, with the OIC's own details in place of the parts in angle brackets:

   ```sh
   python manage.py create_oic <username> --first-name <first name> --last-name <last name> --employee-id <employee ID>
   ```

   It prints a temporary password, once. Do **not** run `seed.py` on the cloud: it makes demo accounts that share one password.
2. **Sign in** at the site with that account. OCRIS asks for a new password at once.
3. **Check the address the server sees.** Sign-in limits are counted per address, so the server must see each person's real one. Still signed in as the OIC, open `https://ocris-xxxx.onrender.com/api/server/client-address/` in the same browser:
   - Find your own public address (search "what is my IP" in another tab) and compare it with `address_used`.
   - If they differ, set `TRUSTED_PROXY_COUNT` to the value in `suggested_trusted_proxy_count` under the service's **Environment**, save (Render redeploys), and check again.
   - Check once more from a phone on mobile data, which has a different address.

   Too low a number makes every user share one address, so 20 wrong passwords from anyone lock everyone out for 15 minutes. Too high a number lets a caller choose an address and get round the limit per address (the limit of 5 per username still holds).
4. **Create the other accounts** in the app, on the **Users** page. Each gets a temporary password that must be changed at the first sign-in.
5. **Close the database to the rest of the internet.** In Render, open the service, click **Connect**, then **Outbound**, and copy the addresses listed. In Atlas, replace the `0.0.0.0/0` entry with those addresses. Reload the site to check it still works.

## 7. Backups

Every night at 02:00 (Manila time) the server:

- writes an encrypted backup of the accounts, the MongoDB data and the scans to `/var/data/backups`, and keeps the newest 7 (`BACKUP_KEEP`);
- deletes uploads that were read but never saved, after 7 days;
- checks the audit file. A `WARNING` line in the logs means `verify_audit` found a change.

If the server was down at 02:00, it catches up as soon as it is running again. Search the logs for `Backup written` to see that it happens.

**These backups and Render's snapshots are both on Render.** Keep a copy somewhere else as well, for example every Friday:

1. Set up SSH for the service (Render docs, "SSH"), which needs a key on your computer.
2. Download the newest backup and the audit file:

   ```sh
   scp -s <ssh-address-of-the-service>:/var/data/backups/ocris-backup-20261023-020000.zip.enc .
   scp -s <ssh-address-of-the-service>:/var/data/logs/audit.jsonl .
   ```

3. Store them on a school drive. They can only be read with the encryption key: `python manage.py restore <file>` lists what a backup holds without changing anything, and `decrypt_backup` turns it into a plain zip.

Rehearse a restore once on a development computer with a copy of the cloud's encryption key, so the steps are known before they are needed ([INSTALLATION.md](INSTALLATION.md), section 8).

## 8. Updating the server

Deploys are started by hand (`autoDeployTrigger: "off"` in `render.yaml`), because each one stops the server:

1. Push the change to `main` on GitHub.
2. Outside school hours, open the service and choose **Manual Deploy → Deploy latest commit**.

The server waits up to 85 seconds for a form being read to finish, then stops (a form still waiting for its turn is cut off and must be uploaded again). Database changes (`migrate`) are applied when it starts again. Changing a setting under **Environment** also redeploys.

## 9. Settings

`render.yaml` and the `Dockerfile` set these. Change them under the service's **Environment**. All other settings in [INSTALLATION.md](INSTALLATION.md) work here too.

| Setting | Value on Render | Meaning |
|---|---|---|
| `DATA_DIR` | `/var/data` (Dockerfile) | The persistent disk. Accounts, scans, the audit file and backups go here |
| `FRONTEND_DIST` | `/app/frontend/dist` (Dockerfile) | The built site, served by the same server as the API |
| `SECRET_KEY` | generated by Render | Django's secret key |
| `DATA_ENCRYPTION_KEY` | yours, from step 4 | Encrypts scans and backups |
| `MONGO_URI` | yours, from step 3 | The Atlas connection string |
| `MONGO_DB_NAME` | `ocris_bcs` | Database name in Atlas |
| `BACKUP_KEEP` | `7` | Nightly backups kept on the disk |
| `TRUSTED_PROXY_COUNT` | `1` until checked (step 6.3) | Proxies in front of the server |
| `MAINTENANCE_HOUR` | `2` (default) | Hour of the nightly backup, Manila time |
| `WEB_WORKERS`, `WEB_THREADS`, `WEB_TIMEOUT` | `2`, `4`, `180` (defaults) | The web server: processes, threads per process, seconds a request may take |
| `OCR_MAX_CONCURRENT` | `2` (default) | Forms each process reads at once: with 2 processes, at most 4 forms (about 1.2 GB); further uploads wait their turn |
| `ALLOWED_HOSTS` | not set | Only needed for a custom domain (below) |

Without `DEBUG`, the server requires HTTPS, a real `SECRET_KEY` and `DATA_ENCRYPTION_KEY`, sends no CORS headers (the site and the API share one address), sets the sign-in cookie with `SameSite=Lax`, and has Django's admin site switched off.

**A custom domain** (for example `ocris.` followed by the school's domain): add it to the service in Render, then set `ALLOWED_HOSTS` to that domain. The `onrender.com` address keeps working.

## 10. When something goes wrong

| What you see | Cause and fix |
|---|---|
| The build stops at a `sha256sum` line: `eng.traineddata: FAILED` | Debian now ships a different English model from the one the OCR was measured with. Do not just remove the check: the confidence threshold was set for this model. Ask a developer to install `eng.traineddata` from `tessdata_fast` 4.1.0 in the Dockerfile instead. |
| The deploy fails after `create_indexes` with "MongoDB could not be reached" | `MONGO_URI` is wrong, the password has a character that needs escaping, or Atlas's network access does not include Render's addresses (step 6.5). |
| The deploy fails: "Set DATA_ENCRYPTION_KEY" or "is not a valid key" | The key is missing or was copied incompletely. Paste it again under **Environment**. |
| "Bad Request (400)" on every page | A custom domain is not in `ALLOWED_HOSTS`. |
| The site shows, but signing in goes straight back to the login screen | The cookie is not stored. Open the site at its `https://` address; check that `AUTH_COOKIE_SAMESITE` was not set to something else. |
| The server restarts while several people upload (memory) | Each form being read takes about 300 MB, and at most `OCR_MAX_CONCURRENT` (2) per process are read at once. Lower it to `1`, or choose the next instance size. |
| Everyone is refused sign-in for 15 minutes after some wrong passwords | `TRUSTED_PROXY_COUNT` is too low, so everyone shares one address. Do step 6.3. |
| Uploads take two or three minutes instead of one | Several forms are being read at once and share the one CPU, or wait for their turn (`OCR_MAX_CONCURRENT`). If it happens often, choose an instance with 2 CPUs. |

## 11. What this set-up does not do yet

- **OCR still runs inside the upload request**, 30 to 70 seconds per form. Render allows requests of up to 100 minutes, so it is not cut off, but the number of forms read at the same time is limited by memory (section 10).
- **Tesseract is 5.5.0 on the server** (Debian) and 5.5.3 on the development computer, with the same English model file. Re-check a few forms on the server against the paper before relying on its confidence figures.
- **Accounts stay in SQLite** on the disk, with a copy of each profile (no passwords) in MongoDB's `users` collection. Records, scans and the audit log are in MongoDB.
